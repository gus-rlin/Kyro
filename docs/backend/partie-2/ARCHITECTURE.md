# Architecture de la réalisation P2

2026-10-05 — runtime et fabrique implémentés. Le [rapport de livraison](VALIDATION.md) distingue les essais historiques des preuves de clôture. Le runtime Rust/Axum/PostgreSQL est dans `crates/kyro-app`, la fabrique dans `crates/kyro-factory`, son intégration dans API/Store/worker P1. Les interfaces Leptos et les agents restent hors de cette partie backend.

La fabrique Rust doit lire l'AppSpec immuable de P1, vérifier les manifestes et les autorisations, produire un verrou signé et assembler des sources uniquement depuis le catalogue admis. Les paramètres deviennent du JSON, pas des fragments Rust, SQL ou shell. API et worker de pilotage ne reçoivent aucun accès à la base de données des applications construites. Les secrets des adaptateurs et de l'application sont provisionnés hors sources/images.

## Profil d'isolation local D37

Le profil proposé initialement par la recette mentionnait des VM QEMU/KVM. L'hôte Docker Desktop de réalisation n'expose pas `/dev/kvm`. TCG n'est pas retenu comme frontière de sécurité : la [politique officielle QEMU](https://www.qemu.org/docs/master/system/security.html) exclut ses garanties d'isolation. Variante examinée pour cette réalisation : **gVisor runsc 20260928.0, plateforme systrap**, lancé directement avec bundles OCI, sans modifier le daemon Docker partagé. Le runtime est téléchargé depuis le fournisseur officiel avec SHA-512 fixé ; les sidecars restent à côté du binaire selon sa procédure actuelle.

Les conteneurs externes Docker ne sont que l'enveloppe de supervision des ressources ; chaque workload doit effectivement tourner dans un Sentry gVisor. Construction et vérification ont des rootfs, espaces de travail, identités et données distincts. Aucun socket Docker, checkout partagé, clé d'admission ou clé d'attestation dans le workload. Sources/configuration et critères protégés sont copiés et hashés séparément ; le constructeur ne choisit pas les critères. Les limites de CPU, mémoire, PID, stockage et durée doivent être éprouvées, pas seulement configurées. Un profil indisponible ou non qualifié refuse toute preuve positive.

Références consultées le 2026-10-05 : [installation gVisor](https://gvisor.dev/docs/user_guide/install/), [plateforme systrap](https://gvisor.dev/docs/user_guide/platforms/), [OCI](https://gvisor.dev/docs/user_guide/quick_start/oci/), [rootless](https://gvisor.dev/docs/user_guide/rootless/). Les probes réelles builder/verifier sont conservées dans le rapport. Le contrôleur et le daemon Docker font partie de la confiance opérateur ; les workloads ont capacités vides et UID invité 0 mappé au seul UID extérieur 1000. Cette variante ne prouve ni un daemon rootless ni KVM. Les quotas CPU/mémoire/PID/disque sont effectivement atteints ; le chemin de timeout est éprouvé à 3 s, sans prétendre avoir attendu les plafonds 900/600 s. Un changement d'image, rootfs, renderer ou driver exige une nouvelle qualification.
