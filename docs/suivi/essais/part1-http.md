## Changements

L’assembleur API contient `AppState::new`, les limites de concurrence et de corps, le délai de 30 s des routes ordinaires, les probes live/ready, l’arrêt gracieux, l’ID de requête et les traces à cardinalité bornée. Les modules possédés ajoutent l’enveloppe d’erreur typée, les extracteurs qui n’échoient pas les entrées, les routes jobs, budget/effets et le SSE à curseur projet, avec tests unitaires pour préconditions, curseurs et erreurs. L’exécutable charge une configuration role-scoped API, connecte le rôle API sans lancer de migration et initialise OIDC et passerelle depuis l’environnement.

Après coordination avec les contributions projet et modèle, l’admission `ModelCall` relit le snapshot projet/politique et appelle `Gateway::validate_request` avant l’écriture du job; la politique est liée à la révision CAS. Le SSE relit bounds et événements en lots limités à chaque poll, y compris lorsqu’une purge supprime toutes les lignes conservées. Le budget utilise `ETag: "budget-N"` et `If-Match` comme CAS de version de configuration, pour protéger plafond/devise/échelle ensemble. `DELETE` de job enregistre une demande 202; le Store décide execute-propriétaire ou manage-tiers, et le worker conserve la responsabilité de la transition terminale/réservation. Ces contrats attendent toujours leur compilation avec les modules frères.

Le checkpoint suivant applique D30 à `GET /jobs/{job_id}` : le handler n’impose plus l’autorisation `read` avant le Store, qui peut ainsi accorder au créateur le suivi de sa propre commande de rapprochement avec `budget` ou `manage`; les autres commandes et la liste restent en lecture. Le contrat HTTP et l’opération OpenAPI décrivent cette exception.

Le SSE utilise maintenant `Store::read_event_page` pour lire les limites physiques globales de rétention et jusqu’à 100 événements visibles dans une même transaction. Les séquences visibles peuvent sauter à cause d’événements masqués par l’environnement; le flux ne traite plus un trou comme une purge. Un `410` est réservé à un préfixe réellement purgé (`cursor < earliest_retained - 1`) ou à un historique entièrement purgé avant le compteur global (`earliest_retained` absent et curseur inférieur au dernier numéro). Les tests unitaires ciblent le préfixe purgé, la purge totale, la vue sans événement visible et la reprise au compteur global. Le commit Store exposant cette page atomique est `ffd588660965487f79c2544a725a63d803d082b3`; il doit être intégré avec le commit API pour compiler ensemble.

Les commits de contribution déjà posés sont `acc44ed` (runtime API et contrat) et `172d2e1` (image, exemple, CI). Le workflow est ensuite adapté à l’auditeur fail-closed `scripts/check-dependencies.mjs` de la contribution common; le runner E2E est livré par la contribution d’intégration.

## Clarification de l’observabilité HTTP — 2026-10-03

Après l’alignement sur `gus-rlin/backend-p1@cbb774c` (merge local `22035fe`), `HTTP.md` distingue maintenant les séries Prometheus des traces structurées. La lecture de `crates/kyro-api/src/lib.rs` confirme que le compteur Prometheus est étiqueté seulement par les ensembles fixes `HTTP_METHOD_LABELS` et `HTTP_STATUS_LABELS`, et que l’histogramme de latence n’a aucun label. Le temps est relevé lorsque `next.run` a produit un `Response` avec ses en-têtes; le corps en streaming n’est pas consommé par cette mesure.

Le même middleware renseigne le champ de trace `route` depuis `MatchedPath`, avec le template Axum déclaré ou le fallback `unmatched`; ce champ ne fait pas partie des labels Prometheus. `request_id` est créé par le serveur, tandis que les identifiants de ressource, query strings, headers, cookies et corps ne sont pas copiés dans ces champs. La revue des tests existants `prometheus_metrics_are_emitted_with_only_bounded_labels`, `observability_normalizes_unrecognized_client_methods` et `metrics_route_returns_prometheus_text` confirme les valeurs `OTHER`, les classes standard 1xx–5xx, l’absence de route/UUID dans l’exposition et l’en-tête de format Prometheus. Le sixième label `other` de classe de statut est défini par le code mais n’est pas exercé par ces tests; ceux-ci n’assertent pas non plus directement le champ `MatchedPath`, vérifié ici par lecture du middleware. Ces tests ont été lus, pas relancés; `git diff --check` passe. Il s’agit d’une correction documentaire fondée sur le code et ses tests, pas d’une qualification du runtime métrique ni de la recette E2E en cours.
