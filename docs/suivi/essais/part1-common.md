## Mise à jour — backend JWT après revue de sécurité

- Date : 2026-10-03 (Europe/Paris)
- Objectif et critères : retirer l’usage du backend `rust_crypto` de `jsonwebtoken` 11.1.0 afin de ne plus dépendre de `rsa` 0.9.10 ; conserver les API JWT existantes, régénérer `Cargo.lock` et vérifier sous l’image Linux épinglée.
- État de départ : branche `gus-rlin/part1-common`, HEAD `29147db`; root avait signalé l’avis RUSTSEC-2023-0071 (RSA, aucune version corrigée dans l’avis). Le workspace utilise l’image officielle `rust:1.96.1-slim-bookworm` épinglée au digest amd64 `sha256:39decc9f9f4a87e03db5069b2424c0ee13c3d7e4116010980d4f96849e823bc4`.
- Changements : la dépendance partagée sélectionne maintenant `jsonwebtoken` avec `aws_lc_rs` à la place de `rust_crypto`; le verrou retire les dépendances RustCrypto activées par ce feature et ajoute `aws-lc-rs`. Aucun avis n’est ignoré. La documentation officielle de `jsonwebtoken` 11.1.0 indique qu’il faut choisir au plus un des deux backends et que le feature `aws_lc_rs` active `aws-lc-rs`; la table des features associe explicitement `rust_crypto` à la dépendance optionnelle `rsa` : [README versionné](https://docs.rs/crate/jsonwebtoken/11.1.0/source/README.md), [features versionnés](https://docs.rs/crate/jsonwebtoken/11.1.0/features). Les appels aux clés RSA dans le code identité restent aux mêmes API (`EncodingKey` / `DecodingKey`), confirmées auprès de son agent propriétaire.
- Vérifications : sous l’image et le digest ci-dessus, `cargo check -p kyro-domain` a résolu le nouveau lock ; `cargo check --locked -p kyro-api` a compilé `jsonwebtoken` 11.1.0 et `aws-lc-rs` 1.18.1 ; `cargo test --locked -p kyro-domain` a réussi (7 tests, 0 échec). `cargo tree --locked -p kyro-api -i rsa` et `cargo tree --locked -i rsa` (cible Linux par défaut) n’affichent aucune arête active vers `rsa`.
- Erreurs et limites : le premier essai Linux `cargo audit --version` a indiqué que la commande n’était pas installée dans l’image ; `cargo-audit` 0.22.0 a été installé dans le volume Cargo persistant. Une commande lancée via `sh -lc` a ensuite échoué (`cargo: not found`) car le shell login réinitialisait `PATH`; la même vérification lancée via `sh -c` a passé. Enfin, `cargo audit --json` (base RustSec mise à jour le 2026-10-02T22:27:46+02:00, 1 288 avis) échoue toujours avec une occurrence RUSTSEC-2023-0071 sur `rsa` 0.9.10. Après le changement, l’entrée `jsonwebtoken` de `Cargo.lock` ne dépend plus de `rsa`; le verrou conserve néanmoins `sqlx-mysql`, dont l’entrée référence `rsa`, tandis que `cargo tree` n’indique aucune arête active pour la cible testée. L’audit vérifie le paquet présent dans le verrou et ne passe donc pas encore. Cette cause est étayée par les entrées du verrou et les résultats des commandes, sans exclusion de l’avis. Le test complet de l’API identité de l’autre worktree et la vérification en intégration restent à exécuter après intégration.
- Résultat : correctif du backend JWT et verrou compilables sur Linux ; tests domaine réussis. Résultat de sécurité partiel : la dépendance RSA active via JWT est éliminée, mais l’audit reste en échec sur l’entrée RSA conservée dans le verrou pour `sqlx-mysql`.
- Prochaine action : root intègre le correctif ; examiner séparément pourquoi l’outil signale cette entrée verrouillée sans arête active avant de déclarer l’audit propre. Ne pas ajouter d’ignore RUSTSEC-2023-0071.

## Mise à jour — classificateur d’avis selon le graphe Cargo actif

- Date : 2026-10-03 (Europe/Paris)
- Objectif et critères : distinguer un avis signalé dans `Cargo.lock` d’un paquet effectivement actif pour la compilation Linux, refuser toute vulnérabilité active et échouer fermé sur une commande, un JSON ou un graphe incomplet. Aucun avis ne doit être ignoré.
- État de départ : HEAD `879306d`; `cargo audit --json` signale toujours RUSTSEC-2023-0071 sur `rsa` 0.9.10. Le correctif AWS-LC a retiré RSA du chemin `jsonwebtoken`, mais `Cargo.lock` contient encore `sqlx-mysql` et RSA.
- Changements : `scripts/check-dependencies.mjs` capture l’audit brut vers le chemin obligatoire `--evidence`, lit les paquets verrouillés avec `cargo metadata --locked --format-version 1`, puis construit l’ensemble actif uniquement avec `cargo tree --locked --workspace --target x86_64-unknown-linux-gnu --edges normal,build,dev --prefix none --format '{p}'`. Le parseur exige les cinq racines connues, refuse les lignes inattendues et vérifie chaque paquet de l’arbre contre les métadonnées. Le résumé JSON stdout ne contient ni chemins ni environnement. Pour l’avis uniquement inactif, il annonce explicitement `active_graph_clear_inactive_lock_advisories` et conserve `auditExitCode: 1`; il ne présente donc pas `cargo audit` comme réussi. Une vulnérabilité active, un échec de commande ou un format incomplet produit le code retour 1. Le filtre de plateforme est volontairement porté par `cargo tree`, seul sélecteur d’activité ; les métadonnées non filtrées servent d’index des dépendances, y compris des build-dependencies résolues pour l’hôte.
- Essais et preuves : `node --test scripts/check-dependencies.test.mjs` réussit (7 tests), couvrant l’avis actif refusé, l’avis inactif classifié, les JSON/graphe/arbre invalides, l’échec opérationnel d’audit et l’absence de chemins dans le résumé. L’exécution locale de `node scripts/check-dependencies.mjs --evidence docs/suivi/preuves/cargo-audit-classified-target-linux-20261003.json` renvoie 0 avec une racine de cinq crates, 199 paquets dans l’arbre, un avis verrouillé, zéro vulnérabilité active, et `auditExitCode: 1`. `cargo tree --locked --workspace --target x86_64-unknown-linux-gnu --edges normal,build,dev --invert rsa --prefix none --format '{p}'` affiche `warning: nothing to print` et sort avec 0. Les sorties expurgées et brutes sont conservées dans [le résumé JSON local](../preuves/cargo-audit-summary-target-linux-local-20261003.json), [l’audit brut utilisé par le classificateur](../preuves/cargo-audit-classified-target-linux-20261003.json) et [la capture brute précédente](../preuves/cargo-audit-linux-20261003.json). La chaîne résiduelle est corroborée par les manifests versionnés de [SQLx macros-core 0.8.6](https://docs.rs/crate/sqlx-macros-core/0.8.6/source/Cargo.toml.orig), où MySQL est optionnel et activé par sa feature, et de [sqlx-mysql 0.8.6](https://docs.rs/crate/sqlx-mysql/0.8.6/source/Cargo.toml), qui déclare RSA.
- Erreurs, corrections et limites : le premier lancement local a échoué fermé au rapprochement, car le metadata filtré Linux omettait des build-dependencies hôte Windows présents dans la sortie `cargo tree` lors d’une exécution Windows. Le metadata est maintenant non filtré et sert seulement à identifier les paquets ; l’arbre reste l’unique source du graphe actif cible. Deux défauts de fixtures ont aussi été corrigés avant que les 7 tests passent : code de sortie par défaut déduit d’un JSON invalide et fixture d’arbre contenant six groupes au lieu de cinq. Le démon Docker n’était pas disponible (`dockerDesktopLinuxEngine` absent), donc cette nouvelle commande n’a pas été relancée dans le conteneur Linux épinglé. L’exécution locale sélectionne la cible Linux mais ses build-dependencies peuvent dépendre de l’hôte Windows ; la validation CI Linux reste nécessaire pour confirmer l’arbre identique à celui de l’image supportée.
- Résultat : classificateur et tests implémentés ; avis RSA explicitement identifié comme inactif dans la sortie Cargo examinée, sans ignore. Le résultat brut de l’auditeur garde son code 1. La validation CI sous Linux est encore à faire.
- Prochaine action : faire appeler le script par la CI Linux et conserver son stdout comme résumé ainsi que le fichier `--evidence` comme audit brut ; examiner les deux artefacts avant de conclure sur le statut de sécurité.
