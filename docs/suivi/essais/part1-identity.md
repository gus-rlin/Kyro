# Identité fédérée, sessions et accès serveur — rapport d'essai

## SUIVI-P1-IDENTITY — Implémentation partielle, intégration à vérifier

- Date : 2026-10-03 (Europe/Paris, UTC+02:00).
- Objectif et critères : implémenter OIDC Authorization Code + PKCE S256, flows state/nonce à usage unique, sessions opaques persistées, CSRF/Origin, organisations/memberships et contrôle serveur des grants. Les critères incluent le refus des jetons à issuer/audience/nonce/signature invalides, la révocation effective, les permissions liées au projet et à l'environnement, et des limites DB qui bornent l'admission.
- État de départ : worktree `part1-identity-b`, branche `gus-rlin/part1-identity-b`, HEAD de départ `9d0c3c3` (socle commun initial). Le workspace partagé et les migrations fondation n'étaient pas déclarés dans ce worktree au début; l'intégration des modules/export reste à la charge du root. Les changements ci-dessous n'incluent pas de migration ni de manifest partagé.
- Changements : ajout des types de domaine dans [identity.rs domaine](../../../crates/kyro-domain/src/identity.rs), du stockage dans [identity.rs store](../../../crates/kyro-store/src/identity.rs) et des routes/extracteurs dans [identity.rs API](../../../crates/kyro-api/src/identity.rs). Les flows OIDC et sessions ne persistent que les hash correspondants; le verifier PKCE n'est conservé que jusqu'à consommation serveur. Sessions : tokens opaques aléatoires à 32 octets, rotation/révocation, 8 actives par acteur et maximum global configurable 1–100000, nettoyage par lots de 500. La variable `KYRO_AUTH_MAX_ACTIVE_SESSIONS` est obligatoire en production. Les flows sont plafonnés à 10 000 actifs globalement et 5 par binding navigateur. Les rôles OIDC ne sont pas créés par un login de développement en production; le fournisseur synthétique exige `KYRO_OIDC_SYNTHETIC_PROVIDER=true` et une configuration development loopback.
- Configuration OIDC lue par `AuthConfig::from_env` : `KYRO_OIDC_ISSUER`, `KYRO_OIDC_AUTHORIZATION_ENDPOINT`, `KYRO_OIDC_TOKEN_ENDPOINT`, `KYRO_OIDC_JWKS_URI`, `KYRO_OIDC_REDIRECT_URI`, `KYRO_OIDC_CLIENT_ID`, optionnel `KYRO_OIDC_CLIENT_SECRET`, `KYRO_AUTH_UI_ORIGIN`, `KYRO_AUTH_SESSION_TTL_SECONDS`, `KYRO_AUTH_LOGIN_FLOW_TTL_SECONDS`, `KYRO_AUTH_MAX_ACTIVE_SESSIONS` et `KYRO_OIDC_SYNTHETIC_PROVIDER`. La validation de JWT n'autorise que RS256, exige un `kid` unique dans un JWKS borné et compare issuer, audience, temps et nonce. Les secrets ne sont ni sérialisés ni exposés dans les erreurs.
- Accès : `AuthActor` relit la session active; mutations vérifient `X-CSRF-Token` et, si présent, un `Origin` exactement égal à l'origine UI. L'autorisation vérifie la visibilité RLS avant la permission (projet invisible : 404; projet visible sans action : 403), les grants actifs de l'environnement courant et `resources` égal à `*` ou à l'UUID du projet. Le propriétaire d'organisation existant est requis pour gérer les grants; une cible `manage` doit déjà être owner. Les flows/organisations/grants et le retrait membre reposent sur les fonctions/policies SQL convenues avec foundation; le retrait atomique dernier-owner/révocation des grants reste vérifié avec la migration foundation, non modifiée ici.
- Essais et preuves : `rustfmt --edition 2024` a réussi sur les quatre fichiers Rust possédés. Dans un harness temporaire Linux qui copie les sources vers un workspace minimal, `cargo test --offline -p kyro-api` a réussi avec `rust:1.96.1-bookworm`, `jsonwebtoken 11.1.0` et backend AWS-LC : 9 tests unitaires et 4 tests d'intégration de configuration/erreurs, zéro échec. Un harness temporaire Windows incluant le code `kyro-domain::identity` et `kyro-store::identity` a aussi passé `cargo test --offline -p kyro-store`; la commande a compilé les crates mais n'a exécuté aucun test. Ces résultats sont isolés aux harness et ne prouvent pas la compilation du workspace intégré. Le test PostgreSQL `postgres_persists_flows_sessions_and_organization_membership` est ajouté, marqué `ignore` car il nécessite une base migrée et `KYRO_TEST_DATABASE_URL`; il n'a pas encore été compilé ni exécuté.
- Erreurs et corrections : la première compilation Linux a échoué car l'image Rust nue n'avait pas `cmake`; le shell login a ensuite masqué `rustc`. Après installation de `cmake` dans le conteneur éphémère et usage d'un shell non-login, le harness a compilé avec AWS-LC et les 13 tests ont passé. Une erreur d'exhaustivité liée au nouveau `Error::StaleBudgetVersion` a été corrigée dans le mapping `AuthError`, puis le test repassé. Une tentative de compilation Windows a échoué dans `aws-lc-sys` faute de NASM/environnement Visual Studio configuré; ce n'est pas un résultat de compilation du projet. Après l'ajout du test PostgreSQL, le pipe Docker Desktop n'était plus disponible, empêchant la resynchronisation du harness et l'exécution sur PostgreSQL. Aucune vraie base PostgreSQL n'est donc attestée ici.
- Correction SQL : les continuations de ligne `\` dans les chaînes SQL Rust concaténaient certains mots-clés sans espace. Elles ont été remplacées par des espaces littéraux et les requêtes relues; la suite SQL des migrations reste à valider en intégration.
- Limites et résultat : partiel. Les tests crypto/API du harness temporaire passent, mais les routes ne sont pas encore compilées avec le `AppState` final, le scénario DB ignoré n'a pas tourné, l'authentification n'a pas été testée contre un vrai fournisseur OIDC et les policies/retrait dernier-owner ne sont pas prouvés par une base. Au dernier essai, aucun serveur PostgreSQL Windows n'était installé et les contextes Docker `desktop-linux` et `default` ne répondaient pas. Le module doit être exporté par l'intégrateur; relancer les tests du workspace intégré puis le test PostgreSQL ignoré contre une base fraîchement migrée avant d'annoncer P1 vérifié.
- Prochaine action : intégrer les modules dans le workspace principal; lancer le test ignoré avec `KYRO_TEST_DATABASE_URL` connecté en `kyro_api` sur PostgreSQL migré; compléter le rapport avec les résultats réels et corrections éventuelles.

## D31 — Plafonds de capacité par grant

- Date : 2026-10-03 (Europe/Paris, UTC+02:00).
- Objectif : faire respecter les limites fixées sur un grant sans fusionner les plafonds de plusieurs grants; garder les actions en alternatives OR et utiliser les appels séparés convenus par le worker pour les opérations multi-action.
- Changements : `GrantLimits` refuse les champs inconnus, null, fractionnaires, valeurs hors bornes, omet les `None` en JSON et valide les cinq plafonds; `GrantDemand` transporte les faits calculés côté serveur. La création de grant garde l’ancienne API avec des limites vides et ajoute `create_capability_grant_with_limits`; le DTO HTTP accepte l’objet `limits` optionnel par défaut vide. `authorize_demand_in` verrouille les grants candidats par `id`, relit leur environnement, ressources et expiration, puis demande qu’une seule ligne couvre toutes les dimensions. Les actions de la liste sont alternatives (OR); les opérations exigeant plusieurs actions font des appels séparés avec les mêmes faits. Action non accordée reste Forbidden; action présente mais aucune limite compatible renvoie ResourceLimit. La migration 0012 a été livrée par foundation au commit `c36b0ff0cbec263cb8944c13dab401a49bc69a88`; les exports de modules restent au propriétaire root.
- Essais : `rustfmt --edition 2024` et `git diff --check` ont réussi. Un harness temporaire Windows a exécuté `cargo test --offline -p kyro-domain -p kyro-store` : 10 tests de domaine réussis, store compilé avec 0 test. Un harness temporaire Linux Docker (`rust:1.96.1-bookworm`, backend AWS-LC) a exécuté `cargo test --offline -p kyro-api --lib` : 10 tests réussis, dont le DTO de grant et les contrôles OIDC existants. Ces harness n'incluent pas l'ensemble du workspace intégré. Le test PostgreSQL ignoré contient maintenant la recette d'admission D31 mais n'a pas été compilé/exécuté contre PostgreSQL dans ce checkpoint.
- Limites : pas de preuve runtime d'insertion/lecture JSONB sous la contrainte de migration 0012, ni d'admission sous RLS; le test intégré doit être lancé sur la base P1 fraîche migrée après intégration des commits foundation/root. Les actions multi-requises sont vérifiées par deux appels `authorize_demand_in` singleton, qui ne partagent que les faits de demande et ne combinent pas les plafonds de grants pour une même action.
- Résultat : implémentation D31 prête au checkpoint; validation isolée du domaine, du store et de la bibliothèque API réussie; intégration PostgreSQL encore à établir.

## Correctif — tailles des fixtures du test PostgreSQL

- Date : 2026-10-03 (Europe/Paris, UTC+02:00).
- Objectif : compiler le scénario PostgreSQL d'identité et de limites sur le workspace intégré en respectant les colonnes de hashes SHA-256 de 32 octets.
- État de départ : le contrôle Linux du root au commit `28e06da` signalait 13 erreurs de compilation dans `crates/kyro-api/tests/oidc.rs`; les fixtures utilisaient les 16 octets bruts d'UUID alors que les types store exigent `[u8; 32]`.
- Changements : les hash fixtures state, nonce, browser binding, session token et CSRF sont désormais des SHA-256 de valeurs synthétiques étiquetées par un UUID propre à chaque exécution. Les contrôles de mauvais binding et de plafond de sessions sont conservés; aucun contrat ni contrôle store n'a été assoupli.
- Essais et preuves : une première compilation Docker Linux s'est arrêtée avant Rust, car l'image n'avait pas `cmake`; une seconde tentative avec shell login a installé `cmake` mais échoué car ce shell ne trouvait pas `cargo`. Avec `cmake` installé dans le conteneur éphémère et un shell non-login, `cargo test --offline -p kyro-api --all-targets` sur une copie temporaire du workspace root `28e06da` avec le seul test corrigé a réussi : 23 tests unitaires API et 4 tests OIDC passés, 1 test PostgreSQL ignoré.
- Limites : `KYRO_TEST_DATABASE_URL` n'est pas configurée dans ce worktree, donc le test PostgreSQL n'a pas été exécuté ici. L'agent E2E indique qu'une base jetable `kyro_p1_test_*` est migrée et prévoit l'exécution des tests ignorés après intégration de ce commit; cette recette reste en attente.
- Résultat : compilation Linux all-targets vérifiée sur le workspace intégré et fixtures à 32 octets corrigées; validation runtime PostgreSQL encore à établir.

## Correctif — verrouillage des grants sous RLS

- Date : 2026-10-03 (Europe/Paris, UTC+02:00).
- Objectif : autoriser `kyro_api` et `kyro_worker` à prendre le verrou partagé nécessaire sur les grants pertinents sans accorder un droit UPDATE applicatif.
- État de départ : root a reproduit qu'un acteur avec un grant visible et l'action `write` reçoit `Forbidden` dans `authorize_demand_in`. Le `SELECT ... FOR SHARE` direct sur `capability_grants` est filtré par la policy RLS UPDATE propriétaire, puisque PostgreSQL exige UPDATE pour la clause de verrouillage.
- Changements : la lecture directe est remplacée par `public.kyro_lock_actor_grants($1, $2, $3)`, avec les mêmes colonnes et binds actor/project/actions. Foundation confirme que le helper vérifiera le rôle applicatif, l'acteur transactionnel, l'environnement, la visibilité et l'appartenance, puis verrouillera membership avant les grants actifs compatibles; il n'ajoute pas UPDATE à `kyro_api`/`kyro_worker`. Les vérifications Rust d'action, ressource, environnement, expiration, limites et erreurs restent en place.
- Essais et preuves : après synchronisation du store dans le harness temporaire, `cargo test --offline -p kyro-domain -p kyro-store` a réussi : 10 tests de domaine passés, store compilé. `rustfmt --edition 2024` et `git diff --check` réussissent. La migration foundation 0015 est en cours; le test PostgreSQL du worker limité doit être relancé après intégration du helper.
- Limites : aucune vérification SQL runtime du helper 0015 dans ce worktree ancien; le résultat E2E PostgreSQL limité-writer est en attente. Le test OIDC précédent de persistance des flows avait aussi été signalé en échec `Forbidden` à la création du flow; ce correctif ne touche pas `create_login_flow`.
- Résultat : requête store réorientée vers le verrouillage borné foundation; compilation du store vérifiée, résultat PostgreSQL à établir après migration 0015.
